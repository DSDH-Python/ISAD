第 7 章　复杂工作流与多智能体系统

当任务变复杂：用业务逻辑节点与多 Agent 协同攻坚。本章掌握选择器/批处理/循环/代码节点，理解工作流嵌套与多智能体分工。

第一部分　课程导学

导语 · 本章定位

简单任务一个工作流搞定；复杂任务需要"逻辑分支 + 并行 + 协作"。本章是工程能力的分水岭——把庞大流程拆成可调试的模块（嵌套工作流），让多个专长 Agent 像团队一样分工（多 Agent）。这背后是业务流程管理与多智能体系统（MAS）的经典理论。

三维学习目标
知识
理解业务逻辑节点；掌握工作流嵌套；了解多 Agent 模式。
能力
能用代码/批处理/循环节点；能通过嵌套实现模块化；能设计多 Agent 协同。
价值
培养模块化工程思维；培养精益求精的工匠精神；提升分析复杂问题的能力。

理论基石 · 信息系统分析与设计

理论 · 业务流程与工作流理论

BPMN（业务流程建模与标注，统一流程图形语言）；WfMC（工作流管理联盟参考模型：流程定义/引擎/客户端/互操作）；BPR（业务流程重组，根本性再设计）；Petri 网（并发、同步与资源竞争的严格建模）。

理论 · 多智能体系统（MAS）协调理论

Agent = 角色（Role）+ 目标（Goal）+ 结构（Structure）；协调/协作/协商机制：黑板、合同网、市场机制；组织结构隐喻：将人类团队协作映射为 Agent 分工；与 BPM 映射：流程节点 ↔ Agent 职责。

理论 ↔ 智能体能力 映射
BPMN / WfMC ↔ 工作流编排：节点、引擎、客户端与互操作
BPR ↔ 用智能体重组端到端业务流程，而非仅自动化
Petri 网（并发/同步） ↔ 多智能体并发执行与资源竞争建模
MAS 协调（合同网/协商） ↔ 多智能体任务分配、出价与协商
组织结构隐喻 ↔ 父/子 Agent = 团队分工（角色+目标+结构）

案例导入 · 多智能体协同故障调度

案例 B1-05 基于多智能体协同的故障调度新实践
申报单位：中国移动通信集团福建有限公司

在“人工智能+”行动计划深入推进的背景下，中国移动福建公司将九天大模型能力深度融入通信网络运维体系，开创了AI 赋能传统基础设施智能化升级的创新范式。此举积极响应数字经济发展与数字中国建设战略，以人工智能驱动网络运维从自动化向认知化、自优化跃迁，加速构建以AI 为核心引擎的新质生产力，为通信行业数智化转型树立标杆，助力国家智能化基础设施体系高质量发展。面对日均4500 起故障任务，传统调度模式凸显三大结构性痛点：一是跨域调度定界定位能力不足，重复派单严重；二是传统调度流程依赖预定义、硬编码的传统集成方式，无法适应快速变化的网络环境；三是单故障需6 次通话、20 次信息查询。

导学解读 · 与本章的对接：本章讲工作流编排，最怕的是“为了多智能体而多智能体”。本案例给出了一个可检验的判据：日均 4500 起故障、单故障需 6 次通话与 20 次信息查询——复杂度与规模都已越过单点处理的能力边界，才需要拆分专业智能体并协同。请重点看它的三层设计：PrefixSpan 序列挖掘 + 资源图谱做事件关联（相当于工作流中的条件分支依据）、业务 SLA 模型做优先级判定（相当于路由规则）、“事件调度控制模块”做调度大脑（相当于编排器）。定界定位时长由 40 分钟压缩至 20 分钟、首调准确率提升至 80%，正是工作流优化的直接收益，也是本章学习成果的可量化标尺。

第二部分　课程内容

7.1　业务逻辑节点家族

  • 选择器：条件分支，常配合意图识别做分类，可用"否则"兜底，提升可靠性。
  • 批处理：并行批量，任务相互独立、无依赖，运行次数=数组长度，适合批量生成图像/查询。
  • 循环：串行重复，可依赖上次结果，支持次数/无限/数组循环，可"终止循环"跳出。
  • 代码节点：自定义逻辑（JS/Python），上游数据封装在 params，输出须以对象返回。
  • 变量聚合：读取多路分支第一个"非空值"，避免未运行分支读空报错。

7.2　工作流嵌套：复杂业务的模块化

将庞大工作流拆为单一职责子工作流，遵循模块化思想。主工作流负责任务"调度"与"整合"（如 multiplatform_copywriting：开始→嵌套子流→代码 JSON 转数组→循环→结束）；子工作流专注单项能力（generate_article / adapt_content / text2image），各 3~4 节点独立调试。关键约束：只有已发布的工作流才能被主工作流嵌套调用。

7.3　多 Agent 模式

父 Agent：调度中心，按各子 Agent"适用场景"分发，保留全局配置；不满足时回退父 Agent。子 Agent A/B/C：各具专长（订单/促销/人工），独立提示词与技能。跳转机制：输入满足某 Agent 触发条件即移交（如含"人工/投诉"跳转人工客服）。适用于智能客服、深度报告、虚拟公司等。

7.4　多 Agent vs 工作流

多 Agent：多个具决策能力的智能体动态交互，灵活、可自主规划，适合复杂开放问题，但调试复杂。工作流：执行预设固定流水线，可控、清晰、可视化易调试，适合流程明确、结果可预测的任务。

7.5　代码节点与变量聚合实操

代码节点输入/输出：所有上游数据封装在 params（如 const city = params['city']）；输出必须对象返回（即使单值）。能力：数据转换、计算、调外部 API。变量聚合"取首个非空"避免分支不确定性报错。组合案例：合同金额审查 = 读取→解析(大模型,Object)→代码(Python审查)→报告；知识问答 = 联网/头条/大模型三路并行，变量聚合按优先级取首非空。

本章学习方法 · 结对编程 / 角色扮演法（Pair & Role Play）

核心理念：让两个「角色」(如架构师 + 审查员)互相质疑，或你与 AI 结对，能在协作中暴露盲区——比独自闷头写更稳。

四步/要点：① 分角色设定设计者与质疑者两类视角　② 出方案设计者给出架构 / 流程方案　③ 挑漏洞质疑者从边界 / 异常处发难　④ 迭代收敛据反馈修订，直至双方认可

与录屏结合：录屏时，扮演「主管 Agent」给两个子 Agent 派活，演示「角色分工如何提升复杂任务质量」。

📋 实验任务书

目标：实现一个复杂工作流或多 Agent 原型，体现模块化与协同。

环境：任一支持流程编排或多智能体协作的工具；也可用流程图和角色模拟完成概念验证。

交付物：架构图 + 代码节点逻辑说明 + 分流测试记录（≥3 类输入）。

评分点：逻辑正确性(30%) · 模块化(25%) · 多Agent/嵌套(25%) · 测试记录(20%)。

🛠 分步操作 · 构建复杂工作流或多 Agent 系统

动手 · 分步操作
  1. 用代码节点 + 变量聚合，为项目实现一段结构化业务逻辑（如合同/表单审查）。
  2. 或把已有工作流改造为"主工作流 + 子工作流"嵌套结构。
  3. 进阶：搭建多 Agent 原型（父 Agent 调度 + 2~3 个专长子 Agent，如订单/促销/人工客服）。
  4. 测试不同用户输入的自动分流与协同效果。

拓展案例 · AgentOS 集群与联邦协同

案例 B7-06 多智能体集群与联邦协同平台
申报单位：中国电信股份有限公司研究院

电信研究院面向复杂任务协同合作场景，研发“AgentOS”多智能体集群与“AgentFed”联邦协同平台。目前，单一智能体能力边界受限，无法独立完成长流程、多角色、跨系统参与的复杂任务，并且在实现多人、多机器协同时，存在上下文割裂，任务接续困难、协作效率低下的问题。为解决上述问题，平台采用端云协同架构设计：通过AgentOS 构建本地智能体运行底座，提供任务规划、流程路由、指令执行、工具调用、工作流记忆及集群协同全链路能力；通过AgentFed 打造云端联邦协同层，实现跨设备、跨用户上下文与工作空间安全共享。

看点：AgentOS 用 Plan-Route-Action 三层编排把“规划—路由—执行”拆开，AgentFed 则解决跨设备、跨用户的上下文接续。前者是工作流引擎的骨架，后者是协作记忆的载体。
